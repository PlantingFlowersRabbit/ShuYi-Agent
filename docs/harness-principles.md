# Harness 原则

## 核心判断

NovelVoice-Agent 的 harness 不是更长的提示词，而是一套让 AI worker 能持续做正确工作的环境：清楚目标、稳定事实源、可执行验收标准、真实运行证据、资源许可证记录、模型输出校验和失败经验沉淀。

v0.1 不追求全自动生成整章配音，而是先建立可观察、可校正、可复核的人机协作工作流。

## 原则

### 1. 人负责方向，Agent 负责执行和取证

用户定义小说、角色、音色取舍和最终是否可用。Agent 负责拆任务、写代码、跑检查、保存证据、记录失败并修复。

### 2. 仓库是事实来源

对 Agent 不可见的知识等于不存在。项目目标、目录结构、验收标准、资源许可证、模型 provider、TTS 运行方式和失败经验都必须写入仓库。

### 3. 先可观察，再自动化

后续想做 harness 全流程自动化前，必须先让系统能观察：

- 章节和段落解析结果。
- 段落确认状态。
- LLM 原始输出和 repair 结果。
- 文本守恒校验报告。
- 子语句人工修改记录。
- TTS 请求和响应元数据。
- 输出音频路径、时长和可解码状态。

### 4. 把主观质量拆成可验收标准

“划分合理”“声音像”“UI 顺手”不能直接作为验收。要拆成可检查项：

- 文本是否守恒。
- 角色是否来自角色卡或标记人工复核。
- 情绪、语速、音量是否在合法范围。
- 音频是否非空且可解码。
- UI 是否展示确认门禁。
- 角色卡更新后选择器是否同步。

### 5. 生成者和评估者分离

写实现的 Agent 不审自己。测试作者、覆盖核对者、视觉复核者、音频复核者和综合 reviewer 必须是独立角色，且默认只读复核。

### 6. 真实环境优先

涉及模型、TTS、音频和 UI 的验收必须尽量在真实环境运行。mock 只能用于单元测试，不能替代端到端验收。

### 7. 失败要沉淀成规则

解决过的问题必须写入 `docs/experience-library/lessons.md`。高频、关键、容易复发的问题提炼到 `docs/experience-library/active-rules.md`。

## 默认工作流

1. 读取 `AGENTS.md` 和本轮相关 spec。
2. 读取 `docs/development/acceptance-standard.md`。
3. 明确本轮最小目标和不做范围。
4. 由 `test-author` 写测试或检查清单。
5. 由 `acceptance-checker` 查验收覆盖。
6. 补必要观测工具。
7. 由 `builder` 实现。
8. 在真实环境运行验证。
9. UI 交 `visual-reviewer`，音频交 `audio-reviewer`。
10. 综合交 `reviewer`。
11. 主 Agent 汇总证据和风险。

## 不要做的事

- 不用聊天记录替代仓库文档。
- 不把模型输出当成最终事实。
- 不提交无许可证素材。
- 不把 API key 写进仓库。
- 不提交大型模型权重。
- 不用 mock 结果宣称真实 TTS 可用。
- 不为了测试通过降低验收标准。
- 不让实现者同时担任最终 reviewer。
